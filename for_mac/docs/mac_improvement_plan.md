# mac版 改善実装計画

このドキュメントは、現在の mac版
`for_mac/配布用formac/CaptureSystem`
を、Windows版にできるだけ近づけるための実装計画です。

方針は次の通りです。

- 優先順位は、依頼された順をそのまま採用する。
- Windows版と同じ方法が macOS で難しい場合は、**macOS向け代替案**を採用する。
- まずは「試験運用上の意味が大きいもの」から着手し、その後に復旧性や監督機能を強化する。

---

## 0. 現状整理

現在の mac版は、当初の簡易版からかなり改善されている。

- 開始: `start.sh`
- 撮影本体: `bin/capture.sh`
- 終了: `bin/finish.sh`
- 試験中ネットワーク監視: `bin/network_monitor.sh`
- ロック画面: `bin/lock_screen.sh` + `bin/lock_screen.swift`
- 常時最前面バー: `bin/status_bar.sh` + `bin/status_bar.swift`
- 状況確認: `Check.app`
- 保存フォルダ:
  `{学籍番号}_{YYYYMMDD}`
- 画像名:
  `{学籍番号}_{連番3桁}_{HHmmss}.jpg`
- ZIP名:
  `{学籍番号}_{YYYYMMDD_HHMMSS}.zip`
- 解答用フォルダ:
  `~/Desktop/{学籍番号}_{YYYYMMDD}`
  失敗時は `~/Downloads/{学籍番号}_{YYYYMMDD}`
- 画面収録権限チェックあり
- 開始前オフライン確認あり
- 試験中ネットワーク監視あり
- ネット接続時ログ記録あり
- ネット接続時ロック画面あり
- USB + TA PIN による解除あり
- 解除時の Wi-Fi オフ確認あり
- 当日未提出データの再開あり
- 提出済み ZIP からの復元再開あり

一方で、Windows版との差分として残っている大項目はまだある。

- マルチモニタ全体キャプチャは未対応
- USB / 証明書ベースの TA解除は未対応
- `swift` 実行環境に依存するUI実装を採用している

以降は、未完了項目と保留項目を整理しながら進める。

## 2. 実装方針

### 2-1. 提出フォルダ名と画像名の修正

### 目的

- Windows版と同じ命名規則に近づける。
- 試験データの照合と運用を簡単にする。

### Windows版の基準

- 保存フォルダ名:
  `{学籍番号}_{YYYYMMDD}`
- 画像名:
  `{学籍番号}_{連番3桁}_{HHmmss}.jpg`
- ZIP名:
  `{学籍番号}_{YYYYMMDD_HHMMSS}.zip`

### mac版での実装案

- `Logs` 直下固定ではなく、保存先を次の形に変更する。
  - `CaptureSystemData/{学籍番号}_{YYYYMMDD}`
- 画像名は Windows版準拠に変更する。
- ZIP名もタイムスタンプ付きに変更する。

### 影響箇所

- `start.sh`
- `bin/capture.sh`
- `bin/finish.sh`
- `Check.app` の確認対象パス

### 補足

- 現在の `CaptureSystem/Logs` ベースから構造変更が入るため、後続機能の前に先にやる価値が高い。

---

### 2-2. 常時最前面バーの表示

### 目的

- 試験中に「記録中であること」を学生・監督者が常に認識できるようにする。
- Windows版と同じく、学籍番号、枚数、時刻を可視化する。

### Windows版の基準

- 画面上部中央に細いバーを常時表示
- 表示内容:
  `[学籍番号] 試験中: 枚数枚 (HH:mm)`

### mac版での課題

- 素の shell script だけでは常時表示UIを作りにくい。
- AppleScript の `display dialog` は常駐バーには向かない。
- `screencapture` 実行中の裏側で軽量に維持できるUIが必要。

### mac版での候補

1. `Swift` または `SwiftUI/AppKit` の小さな常駐アプリを追加する
2. `osascript` ではなく `swift` コマンドで簡易 Cocoa アプリを起動する
3. 既存の `Check.app` とは別に、バー専用 `.app` を用意する

### 推奨案

- **バー表示専用の小さな macOS アプリを追加**する。
- 起動時に `start.sh` からバーアプリを立ち上げ、PIDで管理する。

### 代替案

- もし常駐バー実装が重い場合は、まずはメニューバー常駐アプリ化を検討する。
- ただし、Windows版の見た目に近いのは画面上部の細いバー。

---

### 2-3. キャプチャ間隔乱数修正（1-59秒）

### 目的

- Windows版の挙動に揃える。

### mac版での実装案

- `jot -r 1 1 59` に変更する。
- 必要なら将来設定値化しやすいよう、`MIN_INTERVAL=1`, `MAX_INTERVAL=59` を定数化する。

### 難易度

- 低い

---

### 2-4. キャプチャ枚数の連番管理

### 目的

- 画像名を Windows版と同様に管理する。
- 欠番や再開時の継続番号も扱いやすくする。

### mac版での実装案

- 当日フォルダ内の既存画像数を数えて開始番号を決める。
- 以後 `001`, `002`, `003` のような3桁連番で保存する。

### 課題

- 再開実装前でも、同一フォルダでの再起動を考えると既存枚数読取が必要。

### 関連

- 「未提出再開」と相性が良いため、先に番号付与方式を整える。

---

### 2-5. マルチモニタ対応

### 目的

- Windows版同様、外部ディスプレイを含む画面全体を取得できるようにする。

### mac版での課題

- 現状は `screencapture -m` によりメインモニタのみ。
- macOS 標準 `screencapture` はオプション次第で挙動が変わるため、安定確認が必要。

### 候補

1. `screencapture` から `-m` を外して全画面取得を試す
2. 複数ディスプレイ時の出力仕様を検証する
3. 必要なら `CGDisplay` ベースのネイティブ補助ツールを作る

### 現在の判断

- `screencapture -m` を外す簡易案は実機で十分な結果が得られなかった。
- 安定実装には、`CGDisplay` 等を使うネイティブ補助実装が必要になる可能性が高い。
- **実装コストと検証コストが高いため、一旦保留**とする。

### 備考

- ここは macOS の制約確認が必要なため、最初に調査タスクを置く。

---

### 2-6. 開始時のオフライン確認機能

### 目的

- Windows版と同様、開始前にオンライン状態で試験を始められないようにする。

### mac版での実装案

- `start.sh` でループ確認を行う。
- 判定候補:
  - `ping`
  - `dns` 解決
  - `curl` / `nc` / `osascript` を用いたHTTP確認

### 推奨方針

- Windows版と同じく、**単一判定ではなく複合判定**にする。
- 例:
  - `ping 8.8.8.8`
  - `dscacheutil` または `host` で DNS 確認
  - `curl` で軽量HTTP確認

### 注意点

- macOS環境によって `ping` や `curl` の挙動差があるため、タイムアウトを短くする。
- 校内閉域網などの特殊環境で誤判定しないか実地確認が必要。

---

### 2-7. 試験中のネットワーク監視

### 目的

- 試験開始後にネット接続が復活した場合を検出する。

### mac版での実装案

- `capture.sh` に監視ロジックを混ぜると保守しづらいので、**別プロセス化**する。
- 例:
  - `network_monitor.sh`

### 推奨方針

- キャプチャと監視を分離する。
- PIDを別管理する。

### 理由

- 将来ロック画面や解除機構を追加しやすい。

---

### 2-8. ネット接続時に警告ログやロック画面表示

### 目的

- ネット接続を検知した際、学生操作を止めて監督対応へ誘導する。

### Windows版の基準

- 警告ログ記録
- 最前面ロック画面
- TA解除まで閉じられない

### mac版での課題

- shell + AppleScript だけで、Windows版のような強力なロックUIを作るのは難しい。
- macOS はシステム全体を完全拘束するUI実装がやや重い。

### mac版での候補

1. AppleScript のダイアログを最前面で繰り返し出す
2. AppKit製のロック画面アプリを作る
3. フルスクリーン警告アプリを別プロセスで常駐させる

### 推奨案

- **最終的には AppKit ベースの警告ウィンドウ**を作る。
- 初期段階では、まず
  - `network_warning.log` を保存
  - 警告ダイアログ表示
  から導入してもよい。

### 段階的導入案

1. ログ記録
2. ダイアログ警告
3. 本格ロックUI

---

### 2-9. TA解除機構

### 目的

- ロック解除を監督者のみに限定する。

### Windows版の基準

- USB上の `TA_unlock.key`
- `ta_unlock.pfx`
- 証明書サムプリント一致
- PIN入力

### mac版での課題

- Windows版と同じ証明書検証フローを shell のみで再現するのは重い。
- USB検知、証明書検証、UI、PIN入力を一体化する必要がある。

### 代替案

1. 最小構成:
  パスワード入力のみ
2. 中間案:
  USB上の特定ファイル + パスワード
3. 本格案:
  `security` コマンドやネイティブ実装による証明書確認

### 現在の判断

- 監督者パスワードのみの解除は、すでに先行実装済み。
- 次段階としては **USB上の特定ファイル + パスワード** が現実的な候補。
- ただし、Windows版のような USB / 証明書 / PIN の完全再現はコストが高い。
- **現時点では一旦保留**とし、必要性が高まった時点で再検討する。

### 理由

- 実装コストと運用性のバランスがよい。
- Windows版完全同等を急ぐより、まず監督者以外が解除しづらい構成を作る方が現実的。

### 2-10. 提出時、ZIPを解答用フォルダへ誘導

### 目的

- Windows版と同様、提出データを解答ファイルと同じ場所に集約する。

### mac版での候補

1. デスクトップに `{学籍番号}_{YYYYMMDD}` を作る
2. ダウンロードをフォールバックにする
3. 開始時点で解答用フォルダを作成する

### 推奨方針

- 開始時に次を作る。
  - `~/Desktop/{学籍番号}_{YYYYMMDD}`
  - 失敗時は `~/Downloads/{学籍番号}_{YYYYMMDD}`
- 提出ZIPはそこへ配置する。

### 影響

- `start.sh`
- `finish.sh`

---

### 2-11. 当日の未提出データがあれば再開する

### 目的

- 再起動や誤終了があっても続行しやすくする。

### mac版での実装案

- 内部保存先を日付付きフォルダへ変更したうえで、
  当日の `{学籍番号}_{YYYYMMDD}` を検出する。
- 画像や `student_id.txt` が残っていれば再開する。

### 必要な前提

- 保存先構造を Windows版寄りに変更済みであること
- 連番管理が入っていること

### 推奨方針

- `start.sh` 起動時に
  - 当日フォルダの存在確認
  - `student_id.txt` の有無確認
  - PID死活確認
  を行い、再開判定する。

---

### 2-12. 提出済みZIPが見つかれば復元再開する

### 目的

- 誤って提出処理をしてしまった後でも、当日の試験を継続できるようにする。

### Windows版の基準

- 解答用フォルダ内のZIPを検出
- 展開
- 保存領域へ復元
- 再開

### mac版での実装案

- 解答用フォルダ内の当日ZIPを検索する。
- 一時ディレクトリに展開する。
- 内部保存先へ戻す。
- `student_id.txt` と画像群が復元できたら再開する。

### 注意点

- ZIP命名規則を先に Windows版寄りへ揃える必要がある。
- `unzip` 失敗時のロールバック設計が必要。

## 4. 保留判断の理由

- マルチモニタ対応は、現行の `screencapture` ベースでは十分な結果が得られず、ネイティブ補助ツール化が必要になる見込みである。
- USB等を用いた TA解除は、Windows版に近づけようとすると USB検知、秘密情報管理、解除UI、運用手順の整理まで必要になる。
- どちらも **実装コストだけでなく実機検証コストも高い**。
- 現在の mac版は、単一モニタ前提かつ TA用USB + TA PIN運用であれば、試験運用としてかなり実用的な水準まで来ている。

## 5. 他端末互換性メモ

他の mac端末で動かすうえで、コード上の主な注意点は次の通り。

- `start.sh`, `network_monitor.sh`, `capture.sh`, `finish.sh` で使っている
  `osascript`, `screencapture`, `caffeinate`, `chflags`, `curl`, `dscacheutil`, `zip`, `jot`
  は通常の macOS に標準搭載されている。
- 一方で、常時バーとロック画面は `swift` コマンドで起動している。
  そのため **Command Line Tools / Swift 実行環境が未導入の端末では動かない可能性がある**。
- 画面収録権限は、実行に使うターミナルアプリごとに必要。
  `Terminal.app` と `iTerm.app` では権限付与先が別になる。
- `Check.app` は `start.sh` 内で `xattr -cr` を実行しているが、初回配布時の Gatekeeper 挙動は端末差があり得る。

### `swift` について

- 一部の mac では `swift` コマンドがそのまま使える。
- ただし、**完全な意味で「すべてのデフォルト mac で必ず使える」とは言い切れない**。
- Xcode や Command Line Tools の状態に依存するため、他端末展開前に
  `swift --version`
  の確認をしておくのが安全。

## 6. 代替案が必要になりやすい項目

特に macOS で Windows版完全同等が難しい可能性が高い項目は以下。

- 常時最前面バー
- マルチモニタを安定して1枚にまとめる処理
- 試験中のロック画面
- TA解除機構の証明書ベース実装

これらは、必要に応じて次の代替案を採る。

- バー:
  専用アプリ化、またはメニューバー常駐化
- マルチモニタ:
  `screencapture` の挙動次第でネイティブ補助ツール化
- ロック画面:
  ダイアログ警告から段階的導入
- TA解除:
  USBファイル + パスワード、またはパスワードのみ
